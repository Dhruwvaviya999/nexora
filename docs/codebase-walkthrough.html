01What Nexora is

A multi-tenant team workspace with an AI assistant bolted onto its own documents.

One sentence: teams sign up, create a workspace, and inside it run projects, tasks, documents, formal task handovers, comments and notifications — plus an AI assistant that answers questions using that workspace's own uploaded files.

The single most important idea in the whole codebase is the workspace. It is the tenant boundary. Every domain object — a project, a task, a document, a comment, a chat message, an embedding vector — carries a workspace foreign key, and every database query filters on it. If you understand that one rule, most of the backend explains itself.

Two processes, one product

There is no shared runtime between the halves. The frontend is a Node process serving React; the backend is a Python process serving JSON. They only ever speak over HTTP (and one WebSocket). That is the entire connection, and section 08 covers it in detail.

HalfRuns asSpeaksOwns
frontend next dev → :3000 HTML/JS to the browser Screens, forms, client cache, routing
backend daphne/uvicorn → :8000 JSON at /api/v1/…, WS at /ws/… Data, rules, permissions, AI, email

03Backend skeleton: what boots, in what order

config/ is the wiring closet. Five files, and then it's all apps.

config/settings/base.py
Everything shared. Reads .env via django-environ, registers the 15 apps, configures DRF (JWT auth by default, IsAuthenticated by default, page size 20, filter backends), throttle rates, Redis cache, Celery, Channels, SimpleJWT lifetimes, and the whole AI = {…} block. Read this file first — almost every behaviour elsewhere is a knob set here.
settings/development.py
settings/production.py
settings/test.py
Thin overrides on top of base. Dev prints email to the console; test turns off Redis, the broker, SMTP and rate limiting so a 40-endpoint smoke test isn't mistaken for an attack; production tightens TLS and requires real SMTP.
config/urls.py
The routing table. Builds api_v1_patterns — one include() per app — and mounts the whole list under /api/v1/. Also mounts Django admin and the OpenAPI docs at /api/docs/. Versioning is baked in, so a future /api/v2/ sits beside v1 rather than replacing it.
config/asgi.py
The entry point that supports both protocols. ProtocolTypeRouter sends ordinary HTTP to Django and /ws/ to Channels. The WebSocket branch is wrapped in OriginValidator (only your frontend's origin may open a socket) and then JWTAuthMiddleware (pull the user out of the ?token= query param).
config/celery.py
Creates the Celery app, pulls all CELERY_* settings out of Django settings, and auto-discovers tasks.py in every app. Imported from config/__init__.py so @shared_task binds correctly no matter how the process started.

How a request actually reaches your code

  1. 01
    config/urls.py

    URL matched against api_v1_patterns, e.g. /api/v1/tasks/ → apps.tasks.urls.

  2. 02
    apps/<app>/urls.py

    A DRF DefaultRouter maps the verb + path to a viewset method: GET /→list, POST /→create, GET /{id}/→retrieve, and so on.

  3. 03
    authentication

    JWTAuthentication reads Authorization: Bearer …, verifies the signature, and sets request.user. No header, or a bad one → 401.

  4. 04
    throttling

    Default 60/min anonymous, 1000/hour per user; tighter named scopes for login, register, password_reset and ai. Counters live in Redis so they're shared across worker processes.

  5. 05
    viewset

    get_queryset() narrows to the user's workspaces; the serializer validates input; permission classes check the role.

  6. 06
    database

    The ORM query runs against Postgres. On write, post_save signals fire — which is how audit rows and notifications appear without any view code asking for them (section 15).

  7. 07
    response

    Serializer renders JSON. List endpoints wrap it as {count, next, previous, results} — that shape is what Paginated<T> in the frontend types mirrors.

04apps/common — the spine

Five small files that every other app inherits from. Understand these and the other 14 apps are mostly configuration.

models.py — the base class chain

TimeStampedModel   created_at, updated_at
      ↓
UUIDModel          id = UUIDField(default=uuid4)   # safe to expose in URLs
      ↓
BaseModel          UUID + timestamps
      ↓
AuditModel         + created_by, updated_by  (FK to User)
      ↓
WorkspaceScopedModel  + workspace  (FK, CASCADE)   # ← the tenant boundary

Task, Project, Document, Handover, AIConversation and PromptTemplate all subclass WorkspaceScopedModel, so they get a UUID id, timestamps, who-created/ who-updated, and a workspace — for free, in one line.

The related_name="%(class)ss" trick means each concrete model gets a sensible reverse accessor automatically: workspace.tasks, workspace.projects, workspace.documents.

viewsets.py — WorkspaceScopedViewSet

This is where multi-tenancy is actually enforced on reads:

def get_queryset(self):
    return self.queryset.filter(
        workspace__members__user=self.request.user   # ← you only see your workspaces
    ).distinct()

And on writes, perform_create checks you're a member of the target workspace before saving, and stamps created_by/updated_by. A subclass then only declares its serializer, filters and search fields — see apps/tasks/views.py, which is 15 lines total for a fully paginated, filtered, permission-checked CRUD API.

permissions.py — the role gates

ClassPasses for
IsWorkspaceMemberany member of the object's workspace
IsWorkspaceManagerowner, admin, manager — the review roles
IsWorkspaceAdminowner, admin
IsWorkspaceOwnerowner only (delete, transfer ownership)
IsWorkspaceAdminOrReadOnlymembers read, admins write

Each resolves the workspace from the object under check — if the object is a workspace use it directly, otherwise use obj.workspace — so one class guards both a workspace and everything nested inside it.

channels_auth.py & throttling.py

JWTAuthMiddleware exists because the browser's WebSocket API cannot set an Authorization header. The token rides in the query string instead, which is why it is short-lived (15 min) and the socket runs over wss:// in production. throttling.py defines the named rate-limit scopes; credential endpoints are keyed by IP, not user, because the attacker you're stopping doesn't have an account yet.

The pattern to notice

Apps never import each other's logic. comments knows nothing about notifications; tasks knows nothing about the audit log. Cross-cutting behaviour is wired by signals (section 15) and small service functions. That's why you can delete the ai app and the rest still runs.

06Frontend skeleton: App Router and route groups

Parentheses in a folder name group routes without appearing in the URL.

src/app/layout.tsx
The root HTML shell. Loads fonts, sets metadata, and mounts <Providers> once for the whole app.
src/app/providers.tsx
The client-side provider tree: QueryClientProvider (TanStack Query cache) → ThemeProvider → AuthProvider → toasts. One singleton QueryClient in the browser, a fresh one per request on the server so no data leaks between users.
src/app/(auth)/
Signed-out screens: login, register, forgot-password, reset-password. Its own minimal layout — no sidebar.
src/app/(app)/layout.tsx
The signed-in shell. Blocks rendering until useAuth() resolves, bounces to /login if the session is dead, then wraps everything in WorkspaceProvider and renders sidebar + header + notification bell.
src/app/(app)/…
One folder per screen: dashboard, projects, tasks, documents, handovers, activity, analytics, ai, settings. Dynamic routes use [id]; each can supply a loading.tsx skeleton.
src/proxy.ts
Runs at the edge before any route renders. Checks only whether an auth cookie exists — no JWT verification — and redirects accordingly. Cheap gate; the real check happens in the layout and on the API.
Naming mismatch

The README calls this file middleware.ts; on disk it is src/proxy.ts exporting proxy(). Next.js 16 renamed the concept — same job, new name. Worth fixing in the README so nobody hunts for a file that isn't there.

07The five frontend layers

Data flows down this stack in exactly one direction. A page never calls fetch itself.

What each layer is responsible for

config/env.ts

Validates NEXT_PUBLIC_API_URL with a zod schema at import time. A misconfigured deploy fails immediately with a clear message instead of producing weird 404s later.

lib/constants.ts

Every API path and every client route, in one object. Nothing hard-codes a URL string. API_ROUTES.tasks.detail(id) is the only way to build a task URL.

lib/api/client.ts

The single fetch wrapper. Injects the JWT, JSON-encodes bodies (but leaves FormData alone so file uploads keep their multipart boundary), builds query strings skipping empty values, and normalises every non-2xx into {status, message, details}.

lib/api/<domain>.ts

One module per resource. Pure functions returning typed promises — tasksApi.list(), .get(), .create(). Also holds toTaskPayload()-style converters that turn form values (empty strings) into what the API wants (nulls).

hooks/use-<domain>.ts

TanStack Query wrappers. Own the cache keys, the enabled guards (don't fetch tasks before a workspace is chosen), and the invalidation rules after mutations.

lib/validations/*.ts

Zod schemas mirroring the backend's constraints, fed to react-hook-form. Catches bad input before it ever leaves the browser; the server still validates independently.

The two providers that everything reads

AuthProvider holds {user, isLoading, isAuthenticated, login, logout}. On mount, if a token cookie exists it calls GET /auth/me/ to confirm the session is real. logout() blacklists the refresh token server-side, clears cookies, and wipes the entire query cache — important, or the next user on that browser would briefly see the previous one's data.

WorkspaceProvider holds the active workspace, persisted in localStorage under nexora.activeWorkspace. Nearly every list query passes activeWorkspaceId as a filter — which is why switching workspaces in the sidebar refreshes the whole app's data without a page reload.

08How the two halves connect

Four mechanisms, and that is genuinely all of it.

1. The base URL

NEXT_PUBLIC_API_URL=http://localhost:8000/api/v1 lives in frontend/.env.local. The NEXT_PUBLIC_ prefix means Next.js inlines it into the browser bundle at build time. In Docker that value must be an address a browser can reach — localhost:8000, never the internal service name web:8000, which is why compose passes it as a build arg rather than a runtime env var.

2. CORS

The browser refuses cross-origin calls unless the server allows them. Django's corsheaders middleware sits near the top of the stack and answers with Access-Control-Allow-Origin for anything in CORS_ALLOWED_ORIGINS (http://localhost:3000 in dev). If you ever see a request that works in curl but fails in the browser with no useful error, this is the first thing to check.

3. JWT in cookies (and why cookies, not localStorage)

Login returns {access, refresh, user} as JSON. The client stores both tokens in cookies — nexora.accessToken and nexora.refreshToken, SameSite=Lax, 7-day max-age. The reason is proxy.ts: the edge guard runs on the server, before React exists, and can only read cookies. localStorage would be invisible to it.

They are deliberately not httpOnly — the backend returns them in the response body, so JavaScript owns them anyway. The file's own comment flags this as a later-phase improvement (move the refresh token to an httpOnly cookie).

Transparent refresh — the nicest bit of the client

  1. 01

    Access token expires after 15 minutes. Next request gets 401.

  2. 02

    client.ts catches the 401 and calls getRefreshedToken(), which POSTs the refresh token to /auth/refresh/.

  3. 03

    Single-flight: a module-level refreshPromise means ten concurrent 401s share one refresh call, not ten.

  4. 04

    New tokens stored, the original request is retried once (_isRetry guards against an infinite loop). The user notices nothing.

  5. 05

    If refresh fails, cookies are cleared → AuthProvider sees no user → the app layout redirects to /login.

Backend side: ROTATE_REFRESH_TOKENS and BLACKLIST_AFTER_ROTATION are both on, so each refresh issues a new refresh token and burns the old one. A stolen refresh token stops working as soon as the real user refreshes.

4. The WebSocket

lib/realtime.ts takes the API URL, swaps http→ws / https→wss, and replaces the path with /ws/notifications/?token=…. Section 11 walks the full round trip.

09Flow: signing in

Follow one click all the way through both halves.

  1. 01
    login-form.tsx

    react-hook-form validates against the zod schema in lib/validations/auth.ts. Bad email never leaves the browser.

  2. 02
    auth-provider.tsx

    login() calls authApi.login() → apiClient.post("/auth/login/", …, {skipAuth: true}).

  3. 03
    accounts/views.py · LoginView

    Subclasses SimpleJWT's TokenObtainPairView, throttled at 10/min per IP. EmailTokenObtainPairSerializer verifies the password and adds the serialized user to the response, so the client doesn't need a second round trip.

  4. 04
    token-storage.ts

    Both tokens written to cookies.

  5. 05
    React state

    setUser(res.user) → isAuthenticated flips true → (app)/layout.tsx stops showing the spinner and renders the shell.

  6. 06
    proxy.ts

    From now on, a request to /login sees the cookie and bounces to /dashboard instead.

Password reset, in the same shape

POST /auth/password-reset/ always answers 202, whether or not the address exists — otherwise the endpoint becomes a way to test which emails are registered. The link carries a base64 uid and a token derived from the user's password hash and last-login time, so it self-invalidates once used or once the password changes. On confirm, _blacklist_all_refresh_tokens() revokes every outstanding session, because refresh tokens outlive the reset by days and whoever prompted the reset might be holding one.

10Flow: creating a task

The representative CRUD path. Every other resource works identically.

  1. 01
    task-form.tsx

    Zod-validated form. toTaskPayload() converts "" → null for optional dates and the assignee.

  2. 02
    use-tasks.ts

    useCreateTask() mutation fires tasksApi.create(payload).

  3. 03
    TaskViewSet.create

    Router mapped POST /api/v1/tasks/ here. WorkspaceScopedViewSet.perform_create confirms membership, then stamps created_by / updated_by.

  4. 04
    TaskSerializer.validate

    Two real rules live here: workspace is derived from the project (attrs["workspace"] = project.workspace), never accepted from the client; and an assignee_id must belong to that workspace or it's a 400.

  5. 05
    Postgres

    Row inserted. post_save fires.

  6. 06
    activities/handlers.py

    An Activity row is appended — task.created, actor, workspace, {title, status} metadata. The task app never asked for this.

  7. 07
    cache invalidation

    onSuccess calls qc.invalidateQueries({queryKey: ["tasks"]}). Every mounted task list refetches; the new row appears everywhere at once.

Why the list query is fast

TaskViewSet.queryset uses select_related(...) on all six FKs, so serializing 20 tasks with their nested assignee, reporter and project is one SQL query, not 120. Every viewset in the repo does this.

11Flow: a live notification

Someone @-mentions you in a comment on a task. Here is the bell lighting up.

  1. 01
    mention-textarea.tsx

    The autocomplete inserts a token into the comment text: @[Dhruw Vaviya](7c3f…-uuid).

  2. 02
    mentions/services.py

    sync_comment_mentions() regex-extracts the UUIDs, keeps only users who are members of that workspace and aren't the author, creates Mention rows for new ones, deletes rows for mentions removed by an edit, and sends the user_mentioned signal.

  3. 03
    notifications/handlers.py

    Receives the signal and calls create_notification(...). This is the only file that knows "a mention should notify someone" — the mentions app stays ignorant of notifications.

  4. 04
    notifications/services.py

    Row inserted, then delivery is deferred with transaction.on_commit(). Pushing inside the transaction could beat the write to disk, and a client that refetched would find nothing. On rollback, nothing is sent at all.

  5. 05
    Redis channel layer

    push_to_user() sends into the group notifications.<uuid-without-dashes>. Wrapped in a broad try/except — realtime is a convenience, and a dead Redis must never break the comment that triggered it.

  6. 06
    NotificationConsumer

    Every socket that user has open is in that group. Each receives {"type": "notification", …}.

  7. 07
    use-notification-socket.ts

    On message, it does not trust the pushed payload — it calls invalidateQueries(["notifications"]) and refetches over REST. One source of truth; the paginated, filtered list can't drift.

Connection lifecycle

OriginValidator refuses sockets from origins you don't serve (checked against CORS_ALLOWED_ORIGINS, not ALLOWED_HOSTS — those differ the moment the API and app live on separate domains). JWTAuthMiddleware resolves the user from the query token; an anonymous connection is closed with code 4401, and the client then retries at the slowest backoff rather than hammering the server with credentials it already refused. Ordinary drops reconnect on a 1s → 30s backoff ladder. If the socket never opens at all, the bell falls back to polling — the feature degrades rather than disappearing.

12Flow: upload a document, then ask the AI about it

Two halves — ingestion (write time) and retrieval (read time). They meet in one Postgres column.

Ingestion — apps/knowledge

  1. 01
    document-upload-form.tsx

    Sends FormData. client.ts detects it and skips JSON encoding so the browser sets the multipart boundary itself.

  2. 02
    DocumentViewSet

    MultiPartParser accepts the file; it's stored at media/documents/<workspace-id>/<name>.

  3. 03
    knowledge/handlers.py

    post_save on Document → if the file type is extractable, enqueue_document(). Metadata-only edits deliberately do not re-trigger this.

  4. 04
    processor.enqueue_document

    Creates a pending EmbeddingJob, then dispatches the Celery task on commit — otherwise the worker could read the document row before the upload transaction committed. If the broker is down, it falls back to running inline: slow beats lost.

  5. 05
    Celery worker

    process_document_task → process_document(): extract text → chunk_text() → embed → store.

  6. 06
    chunker.py

    ~220-word windows with 40-word overlap, so a sentence spanning a boundary is still retrievable. Deterministic and dependency-free.

  7. 07
    DocumentChunk rows

    _store_chunks() deletes the document's old chunks and bulk-inserts new ones in one transaction — so reindexing is idempotent. Each row carries a 384-dimension pgvector, with an HNSW cosine index for fast nearest-neighbour lookup.

Locked-in number

AI["EMBEDDING_DIM"] = 384 is compiled into the database column by the migration. Switching to a 768- or 1536-dim embedding model needs a new migration altering DocumentChunk.embedding, not just an env-var change.

Retrieval — apps/ai

  1. 01
    ChatView.post

    resolve_workspace(user, workspace_id) is the isolation gate — the workspace arrives in the request body here, not the URL, so DRF object permissions can't do it. Throttled at 30/hour because LLM calls cost money.

  2. 02
    AIMessage (user)

    The user's message is saved first, so history stays consistent even if the LLM call fails.

  3. 03
    rag.answer_question

    security.sanitize_input() caps length and strips injection attempts, then two retrievals run.

  4. 04
    semantic_search()

    Embeds the question, runs CosineDistance against DocumentChunk filtered by workspace, drops anything past distance 0.75, returns the top 6.

  5. 05
    build_structured_context()

    A second, non-vector context: recent projects, open/overdue task counts, and tasks keyword-matching the question. This is why the assistant can answer "what's overdue?" — no document says that.

  6. 06
    providers/factory.py

    Resolves the provider: per-workspace AISettings wins, else the project default. The API key is Fernet-decrypted from api_key_encrypted, or falls back to the env key.

  7. 07
    response

    Returns {answer, sources, confidence}. Confidence is derived from the top similarity score — ≥0.6 high, ≥0.4 medium, else low — and the UI renders it as a badge with the cited chunks in a sources panel.

Failure modes are handled explicitly rather than 500-ing: a DatabaseError (pgvector not installed) returns a 503 with setup instructions, and a ProviderError (bad key, LLM down) returns a 502.

13Flow: the handover review

The one workflow with real state transitions and role gates. It's the app's centrepiece.

  1. 01
    handover-form.tsx

    A member submits: task, recipient, work summary, pending items, resources. Status starts pending.

  2. 02
    perform_create

    Notifies the recipient — "X handed over 'Task title'".

  3. 03
    POST /handovers/{id}/review/

    Two guards, in order: the caller's membership role must be in REVIEWER_ROLES (owner / admin / manager) → else 403; and the handover must still be pending → else 400. That second check is what stops a double-approve.

  4. 04
    on approve

    Status set, reviewer and reviewed_at stamped, and the task is reassigned: task.assignee = handover.to_user. This is the only place a handover touches the task.

  5. 05
    notifications

    Two go out on approval — "this task is now yours" to the recipient, "your handover was approved" to the submitter. On rejection, one, carrying the reviewer's comment.

  6. 06
    GET /handovers/{id}/export/

    reportlab renders a PDF and returns it with a Content-Disposition: attachment header. reportlab is imported inside the method so the app still boots if it isn't installed.

Edit/delete rules sit in perform_update and perform_destroy: only the submitter may edit; only pending handovers may be deleted, by the submitter or a reviewer. Everything else is inherited from WorkspaceScopedViewSet.

14Roles & permissions

Four roles, stored on the WorkspaceMember row. A user can hold different roles in different workspaces.

Capability Owner Admin Manager Member
Create & edit content, comment, submit handovers✓✓✓✓
Review handovers (approve / reject)✓✓✓—
Manage members & invitations✓✓——
Change AI settings & API keys✓✓——
Transfer ownership, delete workspace✓———

Enforcement happens in three places, and all three matter: queryset scoping (you can't even see other workspaces' rows), permission classes (object-level role checks), and serializer validation (e.g. an assignee must be a workspace member). Owner is deliberately not an invitable role — ownership moves only through the dedicated transfer endpoint.

15Signals: how the audit log and notifications write themselves

The decoupling mechanism. No view in the repo calls "log this" or "notify them" for these cases.

activities/handlers.py registers a generic pair of post_save / post_delete receivers per model: 

_register_audited(Project,  "project",  lambda i: {"name": i.name, "archived": i.archived})
_register_audited(Task,     "task",     lambda i: {"title": i.title, "status": i.status})
_register_audited(Document, "document", lambda i: {"title": i.title})
_register_audited(Handover, "handover", lambda i: {"task": i.task.title, "status": i.status})

Adding history for a new model is one line. That's the payoff for the indirection.

The subtle bug this had to solve

Deleting a workspace cascades into every child row, and each cascade fires post_delete — which would try to append activity rows pointing at a workspace that's about to vanish, failing the whole delete on a foreign-key violation at commit. So pre_delete adds the workspace id to a suppression set and post_delete removes it. The rows would have been pointless anyway: Activity.workspace cascades, so they'd die with it.

Notifications work the same way but listen to domain signals rather than model saves: user_mentioned (custom signal from the mentions service) and post_save on Comment for replies. Handover notifications are the exception — those are explicit calls in the view, because they depend on the review decision rather than on the row simply changing.

16Background jobs, email & caching

Redis wears three hats here. Locally you can skip it entirely.

Redis is used asForWithout Redis (local)

That last row is the reason Redis is non-optional in production: with four gunicorn workers and a per-process cache, a "10 logins per minute" limit silently becomes forty.

Email goes through apps/common/email.py's queue_templated_email(), which renders a template from backend/templates/email/ and hands it to a Celery task. Note the second template engine registered in settings under the name "text" with autoescape off: without it, an & in a reset URL renders as &amp; and the link arrives carrying a parameter literally named amp;token. Every plain-text email uses render_to_string(..., using="text").

Celery is tuned for the embedding workload specifically: prefetch multiplier 1 and concurrency 2, because each worker process holds its own copy of a multi-hundred-megabyte transformer model in memory.

17Running it

Two paths. Docker for the full stack, or two terminals for day-to-day work.

Everything, one command

cp .env.docker.example .env
# SECRET_KEY must not contain '$'
# (compose reads it as a variable)
docker compose up --build

Brings up db · redis · web · worker · frontend. Migrations run on start. web and worker share one image and differ only in their command, so they can't drift apart.

Local, two terminals

# terminal 1
cd backend
python manage.py migrate
python manage.py runserver   # :8000

# terminal 2

18Gotchas worth knowing

Things that will bite, and the reason each one exists.

The error you just hit

getaddrinfo failed on the Neon host is a DNS failure, not a Django bug. runserver calls check_migrations() at boot, which needs the database, so a network blip at exactly the wrong moment takes the whole start-up down. The host resolves fine now — rerun the server. If it recurs, ipconfig /flushdns; Neon's free tier also suspends idle endpoints, so the first connect after a sleep can be slow.

NEXT_PUBLIC_API_URL is build-time
Changing it in .env.local after a build does nothing to the shipped bundle. Rebuild. In Docker it must be the browser-reachable address, not the compose service name.
proxy.ts only checks cookie presence
Not validity. A stale cookie gets you past the edge guard; the API then 401s, the refresh fails, and (app)/layout.tsx redirects. That's intentional — verifying JWTs at the edge would be slow and duplicate work.
Workspace is never client-supplied on a task
TaskSerializer derives it from the project. Sending a workspace field is silently ignored — the field is read-only.
SIGNING_KEY, not SECRET_KEY
SimpleJWT rejects the name SECRET_KEY outright, taking the app down at import time. Settings falls back to SECRET_KEY's value when JWT_SIGNING_KEY is unset or blank.
Compose YAML indentation
The web command's continuation line sits at the same indent as the first. Indent it further and the folded block keeps the newline, sh -c gets separate arguments, and uvicorn binds 127.0.0.1 — unreachable through the port map.
pnpm only
The lockfile is pnpm's. npm or yarn will resolve a different tree.
README says middleware.ts
The file is src/proxy.ts. Next.js 16 renamed it; the README didn't follow.
